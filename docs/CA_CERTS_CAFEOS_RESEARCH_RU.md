# Обновление доверенных CA на Wii U / CafeOS с Aroma

Дата исследования: 09.11.2026. Статус: анализ открытых исходников, документации
и локального дампа IOSU 5.5.6; аппаратных тестов и установки нет.

## Вывод

Добавлять современные корневые CA возможно, но у Wii U нет единого файла,
замена которого обновит доверие во всех приложениях. Нужно различать:

1. Системный CertStore IOS-NSEC: DER-файлы и текстовый индекс с ID, группами
   и разрешениями. Используется NSSL и приложениями/службами, работающими через него.
2. Собственный PEM bundle Internet Browser. Его изменение касается браузера.
3. Другие WebKit-приложения и игры со своей реализацией TLS/своим bundle.
4. Контекст NSSL конкретного приложения: CA можно добавить через API,
   вообще не редактируя системный CertStore.

Для первого эксперимента с Aroma предпочтителен небольшой плагин/модуль,
добавляющий выбранные DER CA в NSSL-контексты выбранных приложений.
Для настоящего обновления системной БД необходима работа с индексом CertStore
или его представлением в IOS-NSEC. Это отдельная задача, требующая проверки
метаданных конкретной консоли и способа восстановления.

Обновление CA **не обновляет TLS**. В исследованном IOS-NSEC обнаружен старый
OpenSSL и ограничение версии TLS до 1.0 в исследованных путях согласования.
Поэтому актуальные CA не гарантируют совместимость с современными HTTPS-серверами.

## 1. Где находится системное хранилище

Title ID: `0005001B-10054000`, общий для регионов. В WiiUBrew он обозначен
как `key and cert files`; перечислены версии v0, v5, v16, v17, v20, v32 [1].
Это не означает, что v32 установлен именно на данной консоли.

Путь в пространстве имён IOSU:

```text
/vol/storage_mlc01/sys/title/0005001b/10054000/content/
    certstore_metadata.txt
    scerts/
        CACERT_NINTENDO_CA.der
        CACERT_NINTENDO_CA_G2.der
        CACERT_NINTENDO_CA_G3.der
        ...
    ccerts/
        ...
```

В старом FTPiiU Everywhere тот же каталог обычно показывается как
`/storage_mlc/sys/title/...`; Aroma FTPiiU использует пути `/fs/vol/...`.
Префикс необходимо сверять с реальным списком каталогов FTP-сервера,
а не переносить буквально между разными версиями инструмента [8].

`scerts` содержит доверенные серверные CA. `ccerts` содержит клиентские
сертификаты, рядом могут находиться зашифрованные закрытые ключи. Это разные
назначения: замена клиентских сертификатов не обновляет корневое доверие.

WUT прямо указывает, что перечень системных CA взят из
`0005001B-10054000/content/certstore_metadata.txt` [2]. В текущем заголовке:

| Диапазон ID | Назначение |
| --- | --- |
| 100–105 | Nintendo CA / Nintendo Class 2 CA, поколения G1–G3 |
| 1001–1033 | Коммерческие CA |
| 1900–1901 | Отдельная группа коммерческих RSA 4096 CA |

Сам факт наличия CA в этой БД **не означает**, что каждый TLS-контекст ему
доверяет: приложение выбирает CA по ID, группе либо передаёт внешние CA.
Приложение, явно загружающее только Nintendo CA, не начнёт доверять новому
публичному CA только из-за появления нового файла в `scerts`.

## 2. Как устроен индекс

`certstore_metadata.txt` — текстовые записи с парами `NAME = VALUE`,
разделёнными `;`. Парсер Decaf, основанный на реверсе IOSU, описывает поля [3]:

- `ID`, `TYPE`, `ENCODING`, `PROPERTIES`;
- `CAPABILITY_MASK`;
- `PID` и/или `TID` — разрешения для процессов/приложений;
- `PATHS` — путь или пути к данным;
- `GROUPS` — принадлежность к группам;
- дополнительные размеры для зашифрованных объектов и объектов с ключом.

Это описание подтверждается строками диагностики парсера в локальном IOSU.
Однако настоящий `certstore_metadata.txt` данной консоли в ходе исследования
не получен. Поэтому готовой строки для добавления нового CA здесь нет:
числа TYPE/PROPERTIES/GROUPS и права следует сверять с существующей
записью публичного CA и соответствующими проверками IOS-NSEC. Нельзя считать
неполную реализацию эмулятора установочной инструкцией для консоли.

Чтобы расширить системный CertStore, потребуется:

1. Сохранить исходный content/index и сверить хеши.
2. Добавить отдельный DER-файл и запись с уникальным ID.
3. Задать корректные тип, кодирование, доступ и группу.
4. Убедиться, что нужный потребитель загружает эту группу или новый ID.
5. Обеспечить повторную загрузку метаданных: они читаются при инициализации
   IOS-NSEC; закрытие и открытие браузера само по себе этого не гарантирует.
6. Проверить положительные и отрицательные TLS-сценарии.

Простое копирование `cacert.pem` в этот каталог не регистрирует CA.
Подмена файла существующего ID тоже не равнозначна расширению: старые
потребители этого ID начнут получать другой CA и могут потерять доступ.

## 3. Что подтверждено локальным IOSU 5.5.6

Источник: `evidence/firmware-5.5.6/analysis/ios.elf`.
SHA-256:
`8ac1ae366b2925f66f19b7f50033103f0ecee45847c9198aa78343a8cd9c4e23`.
Исследование выполнено чтением ELF и ARM big-endian дизассемблированием
через установленный на Windows Capstone. Дамп не менялся и не передавался
в Интернет. Ниже адреса для воспроизведения анализа, **не адреса готового патча**.

| Адрес / участок | Наблюдение | Значение |
| --- | --- | --- |
| `0xE100002C` | Вызов `0xE10068C0` при старте NSEC | Инициализация NSSL начинается внутри IOSU |
| `0xE10068D4` | Вызов `0xE100A0C4` | Инициализация CertStore |
| `0xE100A10C–0xE100A11C` | Поиск title; literal pool содержит `0x0005001B` и `0x10054000` | Подтверждение ID хранилища |
| `0xE100A174` | Вызов парсера `0xE100D750` с именем `certstore_metadata.txt` | Индекс загружается при инициализации |
| `0xE100D934–0xE100D93C` | `cmp r1, #0x3e8` и переход при достижении лимита | Лимит парсера: 1000 объектов; это не лимит CA в TLS-контексте |
| `0xE1007A84` | `cmp r5, #0x1000` в ветке внешнего server PKI | В этой ветке проверяется размер входного сертификата: до 4096 байт |
| `0xE1007AC4–0xE1007AD4` | Сравнение счётчика внешних CA процесса с лимитом | Массовая загрузка bundle может упереться в отдельную квоту процесса |
| `0xE1007CBC` | DER/X.509 parsing в ветке внешнего server PKI | Начальный PoC должен передавать отдельные DER-сертификаты |
| `0xE10C3108` | Строка `OpenSSL 1.0.0f 4 Jan 2012` | Старый TLS-движок; возможны модификации Nintendo |
| `0xE1010330–0xE1010348`, literal `0xE10104D4` | Проверка `s->version <= TLS_MAX_VERSION`, предел `0x0301` | В исследованном пути максимальная версия — TLS 1.0 |
| literal `0xE10218D4` | Ещё одно значение предела `0x0301` в коде handshake | Дополнительное подтверждение ограничения версии |

Численное значение квоты внешних CA процесса здесь не установлено.
Нельзя переносить лимит 1000 объектов индекса на эту квоту.

Версия OpenSSL установлена по строке плюс проверке кода согласования,
но не по сетевому захвату на консоли. Это не утверждение о TLS каждого
браузера или игры: отдельный стек приложения необходимо исследовать отдельно.
Cemu использует TLS-библиотеки хоста и не доказывает совместимость
реального CafeOS с TLS 1.2 [11].

## 4. Вариант с Aroma без изменения системной БД

WUT экспортирует из `nsysnet.rpl` [2, 4]:

```c
NSSLContextHandle NSSLCreateContext(int32_t unk);
NSSLError NSSLAddServerPKI(NSSLContextHandle context, NSSLServerCertId pki);
NSSLError NSSLAddServerPKIExternal(NSSLContextHandle context,
                                    const void *cert,
                                    int32_t length,
                                    int32_t unk);
```

Есть также экспорт `NSSLAddServerPKIGroups`; в WUT его сигнатура документирована
не так полно, как перечисленные выше функции. Wiki описывает команды
`/dev/nsec/nssl`: AddServerPKI = `0x05`, Groups = `0x06`, External = `0x07` [5].

Для PoC можно перехватить создание NSSL-контекста выбранного приложения,
вызвать оригинальную функцию и добавить 1–2 выбранных CA через
`NSSLAddServerPKIExternal(context, der, der_size, 0)`. Четвёртый аргумент
WUT пока называет неизвестным; реверс Decaf трактует его как тип сертификата
и допускает значение 0 [3]. Это обоснованное начальное значение для теста,
а не результат аппаратной проверки в этом исследовании.

Практические требования к реализации:

- Ограничить действие Title ID/настройкой, поскольку добавление общего
  публичного доверия в любой контекст меняет исходную политику приложения.
- Загружать и проверять DER с SD заранее, не выполнять файловые операции
  на каждом handshake. Не превышать установленный лимит размера.
- Сохранять исходные проверки сертификатов и имени сервера; журналировать
  результат каждого добавления и параметры ошибки handshake.
- Считать жизненный цикл контекстов, включая уничтожение и повторное
  использование handle; если добавление делается позже создания, не допускать
  повторного добавления при каждом соединении.
- Сначала проверить формат/тип/квоты небольшим диагностическим приложением,
  затем проверять перехват целевого приложения.

Новый CA в одном созданном homebrew-контексте не становится глобальным
и не появляется автоматически в других процессах. PPC-перехват не охватывает
внутренние вызовы NSSL из IOSU-служб. WebKit или игра с собственным TLS
может вообще не вызывать эти функции.

В текущем проекте `aroma_module/nsysnet_shim.c` уже использует FunctionPatcher
и перехватывает `NSSLCreateConnection`. Это показывает наличие подходящей
инфраструктуры, но CA-плагин разумно проверять отдельно от Ethernet-драйвера.
Существующий localhost relay передаёт зашифрованные байты: сам по себе
он не обновляет CA и не добавляет современные TLS-протоколы.

Для полного охвата системных служб потребуется отдельное решение в IOS-NSEC:
например, дополнение данных хранилища в RAM или раннее перенаправление
доступа к файлам. Aroma/Mocha дают основу для доступа к IOSU, но конкретный
универсальный CA-loader здесь не реализован. Нельзя считать обычный PPC
FS-hook перенаправлением всех обращений ARM IOSU к CertStore.

## 5. Браузер: отдельный rootCA.pem

Опубликованный способ 2017 года, проверенный автором на 5.5.1U, —
добавить PEM CA в собственный bundle браузера [6]:

```text
/vol/storage_mlc01/sys/title/00050030/1001200a/content/browser/rootCA.pem  JPN
/vol/storage_mlc01/sys/title/00050030/1001210a/content/browser/rootCA.pem  USA
/vol/storage_mlc01/sys/title/00050030/1001220a/content/browser/rootCA.pem  EUR
```

Здесь формат действительно PEM: последовательность блоков
`-----BEGIN CERTIFICATE-----` / `-----END CERTIFICATE-----`.
Исходные сертификаты при первом дополнении следует сохранить.

Исторический рецепт не является подтверждённым тестом Aroma + 5.5.6.
На второй странице обсуждения есть сообщения, что добавление не решило
ошибки, а также сообщение о зависании. Размер bundle, корректность PEM,
реальный путь загрузки и совместимость TLS требуют проверки.

Для эксперимента без записи в MLC можно проверить подмену через
SDCafiine/ContentRedirection [7]. Ожидаемое размещение для EUR:

```text
sd:/wiiu/sdcafiine/000500301001220A/CA-test/content/browser/rootCA.pem
```

Это **предлагаемый тест**, а не проверенная установка: README SDCafiine
описывает подмену `/vol/content`, но не обещает поддержку конкретного
browser applet и момента чтения его CA bundle. Нужно подтвердить, что
слой подмены установлен вовремя и запрос файла проходит через него.
При отсутствии перехвата нужен отдельный browser-specific FS-hook.

Даже успешная подмена этого файла не обновит системный CertStore, eShop,
Miiverse или произвольную игру. В проекте SSSL прямо выделены WebKit titles
и игры с собственным SSL как отдельные потребители [9].

## 6. Какие CA брать и чего они не исправят

Источник отдельных CA — официальная страница соответствующего центра.
Для Let's Encrypt актуальные корни и цепочки опубликованы в [10].
Практичный первый кандидат для старого RSA-стека — ISRG Root X1,
но успешное добавление корня ещё не доказывает поддержку всей цепочки
и сертификата сервера. На дату исследования Let's Encrypt перечисляет
новые и перекрёстно подписанные цепочки; выбирать нужно по реальной
цепочке целевого сервера, а не только по названию CA.

Рекомендация старого гайда установить DST Root CA X3 устарела:
его срок действия закончился 30.09.2021. Для обычного доступа к сайтам
не требуется и Fiddler CA: это локальный корень для TLS-прокси.

Mozilla bundle в PEM можно получить через curl CA Extract [12].
Это удобный источник для анализа и подготовки набора, но не готовый
формат системного CertStore Wii U. Нельзя слепо передавать целый bundle
в API, которое разбирает один DER CA и имеет квоты. Такой импорт также
не переносит всю политику Mozilla о доверии и ограничениях CA.

Независимо от свежести CA могут помешать:

- требование сервера использовать TLS 1.2/1.3;
- отсутствие общих cipher suites или поддержки нужного алгоритма подписи;
- SNI, особенности проверки SAN/имени, неполная цепочка сервера;
- неправильные дата/время консоли;
- явный список CA/pinning в приложении;
- устаревшие WebKit/JavaScript/HTTP-возможности после успешного TLS.

Если задача — работа произвольного современного HTTPS через NSSL,
потребуется современный TLS-стек на Wii U либо отдельно спроектированный
шлюз. Шлюз с TLS termination сам становится участником TLS и видит данные;
это иная архитектура, чем прозрачный TCP relay. Обновление CA этого не заменяет.

## 7. Inkay/NoSSL/SSSL не являются обновлением CA

В исследованном Inkay `Inkay_Initialize` применяет патч IOSU и прямо
журналирует `Pretendo URL and NoSSL patches applied successfully` [13].
SSSL использует дефект проверки сертификатов в прошивках начиная с 5.5.5 [9].
Оба подхода следует отличать от добавления доверенного CA при сохранении
проверки подписи. Установка Pretendo не доказывает актуальность публичных CA.

При проверке CA-loader нужно контролировать, какие NoSSL-патчи активны.
Обязательный отрицательный тест: недоверенный или неверно подписанный
сертификат и сертификат с неправильным именем должны отклоняться.
Иначе успешный HTTPS не доказывает работу нового корня.

## 8. Рекомендуемый следующий эксперимент

1. Выбрать конкретный потребитель и домен: Internet Browser, определённая
   игра, homebrew или IOSU-служба. Снять ошибку и цепочку сервера.
2. Для NSSL — диагностическое homebrew, импорт одного DER CA и сервер,
   поддерживающий совместимые TLS/ciphers. Сравнить до/после и выполнить
   отрицательные тесты. Для браузера — отдельно проверить чтение rootCA.pem
   и возможность SD-подмены.
3. Только после успешного узкого теста сделать Aroma-плагин с выбором
   приложений и небольшим CA-набором на SD.
4. Если необходимы IOSU-службы — получить штатный индекс конкретной консоли,
   разобрать доступ/группы и проектировать системное дополнение отдельно.

В ходе этого исследования установщик, `.wps` и `.wms` не создавались.
Консоль, NAND/MLC, настройки сети и сертификаты не изменялись.
В WSL UbuntuCafeF проверено только наличие заголовка NSSL; установка,
обновление или изменение SDK/toolchain не выполнялись.
